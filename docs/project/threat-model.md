# Threat model

How touchmark's delivery can be attacked, and for each attack the code that stops it, the tests that show it, and the risk that remains. Nine threats come first, T1 to T9, each named after what the attacker does; then the controls in depth: the isolation of the write key, tokens and git, untrusted input, and the rest of touchmark's security rules. Every row has a test or a recorded residual risk. [Security model](../concepts/security.md) explains the design these tables check.

`TestThreatModelCitesTests` (`internal/cli`) keeps the page honest: every test it names in backticks must exist, and every threat must have its row.

## The boundary

A merge into the hub is code that runs in the targets' CI: a sync pull request comes from a branch of the target repository itself, so the target's workflows run on it with the target's secrets before anyone reviews it. Two things hold the line: the review of the hub, and the isolation of the write account. Everything else (sensitive paths, warnings, guards) helps the reviewer or catches a misconfiguration; it is not a boundary.

The accounts ([Security model](../concepts/security.md)): a **reader** for `plan` in hub pull requests, a **writer** for `distribute` and `doctor` on the default branch only, and the **hub channel**, the CI's own token, which reaches the hub repository alone.

How to read the tests column:

- plain names run in `go test ./...` on every OS;
- *(git 2.45)*: the test needs a git that `plan` and `distribute` support and skips on an older one; the Docker run of the suite (`golang:1.27`, git 2.47, [e2e.md](e2e.md#run)) runs it;
- *(e2e Gitea)*, *(e2e GitLab)*: the live harnesses `scripts/e2e/gitea.sh` and `scripts/e2e/gitlab.sh` (build tag `e2e`);
- *(GitHub fake)*: `ghfake`, an HTTP fake of GitHub; no sandbox organization runs live checks; the bedrock-python hub runs touchmark on github.com ([e2e.md](e2e.md#github)).
